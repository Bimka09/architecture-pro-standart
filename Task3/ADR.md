### <a name="_qmphm5d6rvi3"></a>**Решение**
Для реализации функционала открытия депозитов была выбрана микросервисная архитектура. Приложеные диаграммы описывают структуру системы и ее окружение:

1. [C4 Context](../diagrams/Context.puml)
2. [C4 Container](../diagrams/Containers.puml)

#### Основные компоненты решения:

**Уровень представления:**
- **Веб-интерфейс сайта**: React.js приложение для новых клиентов
- **Интернет-банк**: Веб-приложение на базе ASP.NET MVC 4.5 

**Уровень сервисов:**
- **API Gateway**: Маршрутизация запросов и авторизация
- **Deposit Processing Service**: Микросервис управления депозитными заявками
- **Rate Management Service**: Микросервис управления ставками депозитов
- **Notification Service**: Микросервис уведомлений (СМС, email)
- **Integration Service**: Сервис интеграции с АБС

**Уровень данных:**
- **Deposit Database**: БД MS SQL заявок на депозиты
- **Rate Database**: БД MS SQL ставок

**Интеграционный уровень:**
- **Message Broker**: Асинхронная обмен событиями через Kafka
- **Batch Integration**: Ежедневная синхронизация с АБС


Ключевыми принципами архитектурного решения являются:

1. Минимизация нагрузки на АБС
2. Использование событий (Kafka) для интеграции между сервисами
3. Выделение API Gateway, как единую точку входа для всех клиентских запросов
4. Горизонтальное масштабирование всех компонентов, кроме АБС

#### Логика принятия решений: ####
Выбор микросервисной архитектуры:

- Требование изоляции от АБС (+R6)
- Необходимость независимого масштабирования депозитного функционала
- Возможность независимой разработки и развертывания

Использование API Gateway:
- Централизованная авторизация и аутентификация
- Единая точка мониторинга и логирования
- Возможность маршрутизации запросов между legacy и новыми сервисами

Асинхронная интеграция с АБС:

- Защита критичной системы от перегрузки
- Соответствие техническим ограничениям (batch-интеграция раз в день)
- Возможность обработки пиковых нагрузок через очереди


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

Модификация существующего монолита АБС.

Описание: Реализация всего нового функционала непосредственно в унаследованной системе АБС.
Причина отказа: Данный вариант был отклонен, так как АБС уже перегружена и сложна в масштабируемости (поддерживает только вертикальное).

**Недостатки, ограничения, риски**

**Недостатки:**
1. Сложность архитектуры - увеличение количества компонентов усложняет поддержку
2. Необходимость обучения команд - новые технологии (Kafka) требуют времени на освоение
3. Дополнительная инфраструктура - требуются ресурсы для Kafka, новых сервисов
4. Рост требований к команде к DevOps - для обеспечение доступности и наблюдаемости систем

**Ограничения**
1. АБС масштабируется только вертикально
2. Интернет-банк частично несовместим с Kafka, из-за чего выделен отдельный сервис

**Риски**
1. Потеря сообщений при некорректной настройке Kafka
